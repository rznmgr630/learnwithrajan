<b>Standardizing Python Environments Across Development, Testing, and Cloud Deployments</b><br/>
The classic developer nightmare—*"It worked fine on my machine, but crashed in production!"*—is caused by environment drifts: differing OS C-libraries, mismatched Python minor versions, or missing system dependencies. **Docker** solves this by packaging the Python application, its dependencies, runtime, and OS file system into a lightweight, portable container image.<br/><br/>

<b>1. Virtual Machines (VMs) vs. Docker Containers:</b>
<ul>
  <li><b>Virtual Machines (Heavyweight):</b> Hypervisors virtualize physical hardware. Each VM runs a full guest operating system (Linux/Windows Kernel), consuming gigabytes of RAM and taking minutes to boot.</li>
  <li><b>Docker Containers (Lightweight):</b> Containers share the host operating system kernel and isolate processes using Linux <code>namespaces</code> and <code>cgroups</code>. They boot in milliseconds and consume megabytes of RAM!</li>
</ul>

<b>2. Core Docker Concepts:</b>
<ul>
  <li><b>Dockerfile:</b> A plain-text blueprint containing instructions to build a Docker image.</li>
  <li><b>Docker Image (Read-Only):</b> An immutable, layered snapshot of the application and runtime environment.</li>
  <li><b>Docker Container (Read-Write Execution Instance):</b> A running instance of a Docker image.</li>
  <li><b>Open Container Initiative (OCI):</b> The industry standard specification ensuring Docker images run identically across AWS, GCP, Azure, and Kubernetes clusters.</li>
</ul>

<b>Minimizing Image Sizes and Enforcing Least-Privilege Security</b><br/>
In enterprise production deployments, shipping build toolchains (like `gcc`, `g++`, `make`, `git`) inside production container images creates massive security risks and inflates image sizes.<br/><br/>

**Multi-Stage Builds** solve this by separating the **Build Stage** (where C dependencies and wheels are compiled) from the final **Runtime Stage** (where only compiled artifacts are copied into a clean minimal image).<br/><br/>

<b>1. Multi-Stage Build Pattern:</b>
<ul>
  <li><b>Stage 1 (Builder):</b> Uses a full base image to compile C extensions and build Python wheels into a temporary directory (<code>/root/.cache/wheels</code>).</li>
  <li><b>Stage 2 (Final Runtime):</b> Starts from a fresh minimal `slim` image, copies *only* the compiled wheels from Stage 1, installs them, and discards all compilers and build tools!</li>
</ul>

<b>2. Non-Root Security Hardening:</b><br/>
By default, Docker containers execute processes as the `root` user (`uid=0`). If an attacker exploits a vulnerability in a web framework, they gain root access inside the container and potentially compromise the host system.<br/>
<i>Production Hardening Rule:</i> Always create and switch to a unprivileged non-root user (`appuser`) inside the Dockerfile!

  STAGE 2: Final Production Stage (python:3.11-slim)
  ├── NO gcc! NO make! NO build tools!
  ├── Install compiled wheels: pip install /wheels/*.whl
  ├── Create Non-Root User: USER appuser (uid=10001)

# ==============================================================================

    gcc \\

ENV PYTHONDONTWRITEBYTECODE=1 \\
    PYTHONUNBUFFERED=1 \\
    WORKDIR=/app

WORKDIR \${WORKDIR}

RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels

USER appuser

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
