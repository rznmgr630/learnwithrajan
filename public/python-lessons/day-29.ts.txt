Logging is the process of recording information about what an application is doing while it is running.

When you build a small Python program, you can use print():

print("User logged in")

This is fine while learning Python or quickly testing something.

However, production applications need much more than print statements.

Imagine that your API is running on a production server and a user reports:

"I tried to place an order, but something went wrong."

If your application only contains print statements, you may have no useful information about:

- When the request happened
- Which endpoint was called
- Which user made the request
- Whether the database was available
- What exception occurred
- How long the request took
- Which service failed
- What environment the application was running in

Logging gives you a structured way to record this information.

Python provides a built-in logging module, so you do not need to install an external package for basic logging.

You can start with:

import logging

logging.warning("Something may be wrong")

The logging module provides different levels.

The standard levels are:

DEBUG
INFO
WARNING
ERROR
CRITICAL

These levels communicate how important the message is.

DEBUG is used for detailed information that is mainly useful while developing or troubleshooting an application.

For example:

logging.debug("Received request payload")

You normally do not want huge amounts of DEBUG information in production because it can create unnecessary log volume.

INFO represents normal application events.

For example:

logging.info("User successfully logged in")

INFO messages are useful when you want to understand the normal flow of an application.

WARNING means something unexpected happened, but the application can continue.

For example:

logging.warning("Payment provider response was slower than expected")

The application has not necessarily failed, but the event deserves attention.

ERROR means an operation failed.

For example:

logging.error("Failed to save order")

The application may continue processing other requests, but the particular operation failed.

CRITICAL represents a very serious problem that may prevent the application from continuing correctly.

For example:

logging.critical("Database connection pool is unavailable")

The exact meaning of each level depends somewhat on your application's architecture, but the important idea is that logs should communicate severity consistently.

Real-world example — Web application

Imagine an API endpoint:

POST /orders

A normal successful request might produce:

INFO: Order created successfully

A temporary problem might produce:

WARNING: Payment provider response exceeded expected latency

A failed database operation might produce:

ERROR: Failed to persist order

A complete database outage might produce:

CRITICAL: Database connection unavailable

The levels help developers and operations teams quickly identify what deserves attention.

Logging levels also allow you to control how much information your application records.

For example:

logging.basicConfig(level=logging.INFO)

Now DEBUG messages are ignored by the logger configuration while INFO, WARNING, ERROR, and CRITICAL messages are allowed.

This becomes extremely useful in production.

You may use DEBUG during local development:

INFO
WARNING
ERROR
CRITICAL

But production may use:

WARNING
ERROR
CRITICAL

This reduces unnecessary log volume.

Another important concept is that logging levels are hierarchical.

DEBUG has the lowest standard severity.

CRITICAL has the highest.

If the logging level is configured as WARNING, then WARNING, ERROR, and CRITICAL messages can be emitted, while DEBUG and INFO messages are ignored.

This is useful because you can change the amount of logging without changing every logging statement in your application.

Consider a production server receiving thousands of requests every minute.

If every tiny internal detail is logged at INFO level, the logs can become extremely large.

You may eventually spend more money storing and processing logs than necessary.

Therefore, logging levels are not simply labels.

They are part of your application's observability strategy.

You should ask:

"Who needs this information?"

"How frequently can this event happen?"

"Would this log help someone diagnose a problem?"

"Does this event require immediate attention?"

For example, logging every successful database query at ERROR would make the ERROR level meaningless.

Similarly, logging a complete application failure as DEBUG would hide an important problem.

A good production application uses levels consistently.

A logger is the object your application uses to create log records.

You can create a logger with:

import logging

Then instead of using:

This distinction becomes very important in larger applications.

The __name__ value represents the current Python module.

Suppose your project contains:

app/
    main.py
    users.py
    payments.py

app.users

Inside payments.py:

logger = logging.getLogger(__name__)

the logger name will normally be:

app.payments

This gives you a hierarchy of loggers.

app/

    notifications/
