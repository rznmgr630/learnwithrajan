<b>Version Control for Relational Database Schemas</b><br/>
In production software engineering, database schemas are never static. As business requirements evolve, you must add columns, create indexes, alter table constraints, and drop legacy fields. Running `Base.metadata.create_all(engine)` works fine for brand-new empty databases, but **it cannot modify existing tables without destroying user data**.<br/><br/>

**Alembic** is the official database migration tool built for SQLAlchemy. It acts as version control (like Git) for your database schema.<br/><br/>

<b>1. Why Alembic?</b>
<ul>
  <li><b>Version Control for Data:</b> Tracks every schema change as an incremental revision script with forward (<code>upgrade</code>) and reverse (<code>downgrade</code>) directions.</li>
  <li><b>Zero Data Loss:</b> Modifies database tables safely using DDL (Data Definition Language) without dropping tables or clearing production records.</li>
  <li><b>Team Synchronization:</b> Ensures every developer on the team and every CI/CD deployment pipeline executes the exact same sequence of schema migrations.</li>
</ul>

<b>2. Core Alembic CLI Lifecycle:</b>
<ol>
  <li><code>$ alembic init alembic</code> (Initializes migration directory structure and <code>alembic.ini</code> config).</li>

  <li><code>$ alembic upgrade head</code> (Applies all pending migrations to the latest database version).</li>
  <li><code>$ alembic downgrade -1</code> (Rolls back the most recent migration by 1 revision step).</li>
</ol>

<b>1. Generating Auto-Migrations:</b><br/>

Alembic inspects `Base.metadata`, compares it to the active database table structure, and generates a new Python file inside `alembic/versions/`.<br/><br/>

<b>2. Structure of an Alembic Revision Script:</b><br/>
Every migration file exports an `upgrade()` function (moves schema forward) and a `downgrade()` function (reverts changes):

<b>Managing Migration History and Emergency Rollbacks</b><br/>
When a deployment fails or a newly added column breaks application logic, you must roll back the database schema safely to a previous stable revision state without corrupting database integrity.<br/><br/>

<b>1. How Alembic Tracks Database Version State (`alembic_version` Table):</b><br/>
Alembic creates a special 1-column table inside your target database named <b><code>alembic_version</code></b>. This table holds a single string: the `version_num` hash of the currently active migration head!<br/>
When you run `alembic upgrade`, Alembic reads `alembic_version`, compares it against available revision files, and executes only the un-applied upgrade steps.<br/><br/>

  <li><code>$ alembic downgrade base</code>: Rolls back **ALL** migrations, reverting the database to an empty, un-migrated state!</li>

<b>Executing Database Schema Changes in High-Availability Environments</b><br/>
In enterprise production environments running hundreds of web server instances behind a load balancer, you **cannot** take the application offline to run database migrations. You must execute **Zero-Downtime Migrations**.<br/><br/>

<b>The Golden Rule of Zero-Downtime Migrations:</b><br/>
> *"At any point during a deployment, Old Code (v1) and New Code (v2) are running simultaneously against the Database!"*<br/>
Every schema change must be **backward-compatible** with the older code version currently serving live users.<br/><br/>

<b>1. Dangerous Anti-Pattern (Destructive Single-Step Migration):</b><br/>
Dropping a column or renaming a column in a single migration instantly crashes Old Code (v1) instances that are still querying that column!

<b>2. The Expand-Contract (Parallel Change) Pattern:</b><br/>
To rename a column safely without downtime, execute changes across 3 separate deployment releases:
<ol>
  <li><b>Phase 1 (Expand - Release 1):</b> Add the new column as nullable. Write to BOTH old and new columns in application code.</li>
  <li><b>Phase 2 (Backfill - Release 2):</b> Run a background data migration script copying historical data from old column to new column.</li>
  <li><b>Phase 3 (Contract - Release 3):</b> Update application code to read solely from the new column. Finally, drop the old column in a future release!</li>
</ol>

  Phase 3 (Contract) : Switch code reads to new_col. Safely drop old_col!
