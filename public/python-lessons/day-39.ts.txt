<b>Automated Quality Safeguards and Test Driven Verification</b><br/>
As applications expand in complexity, verifying that new features don't break existing functionality becomes impossible through manual testing alone. **Unit Testing** automates this verification process by writing small, fast test functions that isolate and exercise individual code units (functions, methods, classes) against expected outputs.<br/><br/>

<b>1. Why Use pytest Over Built-in unittest?</b><br/>
Python includes a built-in <code>unittest</code> module, but it requires verbose class boilerplate and specialized assertion methods (<code>self.assertEqual(a, b)</code>, <code>self.assertTrue(x)</code>). **pytest** is the industry-standard testing framework for Python because:
<ul>
  <li>It relies on standard Python <code>assert</code> statements (<code>assert a == b</code>).</li>
  <li>It provides detailed introspection diffs on assertion failures automatically.</li>
  <li>It eliminates class boilerplate—test cases are simple, clean Python functions!</li>
</ul>

<b>2. Automatic Test Discovery Conventions:</b><br/>
When you run <code>$ pytest</code> in your terminal, pytest automatically scans your project directory tree for tests using strict naming conventions:
<ul>
  <li><b>Test Files:</b> Files named <code>test_*.py</code> or <code>*_test.py</code>.</li>
  <li><b>Test Functions:</b> Functions prefixed with <code>test_*()</code> inside test files.</li>
  <li><b>Test Classes:</b> Classes prefixed with <code>Test*</code> (containing no <code>__init__</code> method).</li>
</ul>

<b>3. The AAA Test Structure (Arrange-Act-Assert):</b><br/>
Every clean test function follows the 3-step AAA pattern:
<ol>
  <li><b>Arrange:</b> Prepare input data, objects, and preconditions.</li>
  <li><b>Act:</b> Execute the target function/unit being tested.</li>
  <li><b>Assert:</b> Verify that the actual output matches expected results using standard `assert` statements.</li>
</ol>

Unit testing isn't just about verifying happy-path scenarios where inputs are valid. Production code must handle invalid inputs gracefully by raising appropriate exceptions. <b>1. Testing Exceptions with <code>pytest.raises()</code>:</b><br/>
pytest provides the <code>pytest.raises()</code> context manager to assert that a block of code raises a specific exception type.<br/>

<ul>
  <li>If the code inside the <code>with pytest.raises(...)</code> block raises the expected exception, the test **passes**.</li>

<b>Setup, Teardown, and Dependency Injection</b><br/>
Real-world unit tests often require setting up complex test objects, mock database connections, or temporary test directories before running assertions. <b>1. What is a pytest Fixture?</b><br/>
A fixture is a function decorated with <code>@pytest.fixture</code> that creates and returns a test resource.<br/>
<pre><code>@pytest.fixture
def sample_package():
    return {"id": "TRK-1001", "weight": 15.0, "status": "QUEUED"}</code></pre><br/>

To use a fixture in a test function, simply **pass the fixture function's name as a parameter** in the test function's definition! pytest automatically detects the parameter name, executes the fixture first, and passes its return value into your test.<br/>
<pre><code>def test_package_status(sample_package): # Receives sample_package fixture!
    assert sample_package["status"] == "QUEUED"</code></pre><br/>

<b>3. Fixture Teardown with <code>yield</code>:</b><br/>
If a fixture needs to clean up resources after a test finishes (e.g., deleting temporary files or closing database connections), use <code>yield</code> instead of <code>return</code>!
<ul>
  <li>Code **before** <code>yield</code> executes before the test runs (Setup).</li>
  <li>The value yielded is handed to the test function.</li>
  <li>Code **after** <code>yield</code> executes after the test finishes (Teardown/Cleanup).</li>
</ul>
